# Code-level audit — 2026-09-26

Full code-level review of every production source file in `schema-synchronizer` and
`schema-synchronizer-cli` (~4,300 lines), Maven configuration, Spring wiring, CI/release
workflows, and test coverage. Findings marked **verified** were reproduced against the
compiled code with a scratch harness; the baseline suite (103 unit + 8 CLI tests) passes
clean.

Severity scale: **P0** = breaks advertised functionality or weakens a stated safety
guarantee; **P1** = enterprise-readiness gap; **P2** = hygiene / maintainability.

---

## P0 findings

### P0-1. First change-set apply on MySQL fails (verified)

`DialectSupport.addAppliedByColumnDdl` (DialectSupport.java:65-66) emits the same DDL for
`MARIADB, MYSQL`:

```sql
ALTER TABLE <history> ADD COLUMN IF NOT EXISTS applied_by VARCHAR(200)
```

`DatabaseDialect.supportsAddColumnIfNotExists()` correctly returns `false` for MYSQL, yet
`ChangeSetExecutor.createHistory()` executes this statement **unconditionally** after
creating a fresh history table. MySQL 8.x/9.x does not support `IF NOT EXISTS` on
`ADD COLUMN` (it is a MariaDB-only extension), so the first-ever change-set apply on a
MySQL database dies with error 1064 before any statement runs.

**Why CI never caught it:** `SchemaSynchronizerMySqlIntegrationTest` exercises zero
change sets (`changes = List.of()`), so `createHistory()` is never invoked on MySQL. The
MariaDB path passes because MariaDB supports the syntax.

**Fix:** branch MYSQL separately (probe `INFORMATION_SCHEMA.COLUMNS` or catch/ignore
the duplicate-column error as the Oracle branch already does), and add a MySQL
integration test that applies at least one change set.

### P0-2. `ColumnDefinitionParser` silently drops `NOT NULL` when `DEFAULT` precedes it (verified)

`ColumnDefinitionParser.parse()` removes the `DEFAULT` clause **before** scanning for
`NOT NULL`, and the `DEFAULT` regex is greedy to end-of-string:

```
"TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL"
  -> notNull=false, defaultExpr="CURRENT_TIMESTAMP NOT NULL"
```

Downstream, `NonDestructiveAlterPlanner.plan()` against a live `NOT NULL` column emits:

```
ALTER TABLE t ALTER COLUMN c SET DEFAULT CURRENT_TIMESTAMP NOT NULL   (invalid SQL)
ALTER TABLE t ALTER COLUMN c DROP NOT NULL                            (constraint weakening)
```

The invalid `SET DEFAULT` makes the sync crash with a cryptic syntax error (fail-closed by
luck, not by design), and on any definition where the default expression happened to be
valid with a trailing `NOT NULL`, the parser would silently plan a real `DROP NOT NULL`
constraint relaxation from a pure parsing artifact.

**Fix:** extract `NOT NULL` before `DEFAULT` (mirroring the order the snapshot writer
itself emits: `type NOT NULL DEFAULT ...`). Add parser unit tests for both orderings.

### P0-3. Cross-schema binding bypassable with whitespace around the dot (verified)

`ChangeSetSchemaScope.QUALIFIED` is `IDENT + "\\\." + IDENT` — no whitespace tolerated
around the `.`. Standard SQL accepts `others . victims`, so:

```
ChangeSetSchemaScope.requireScoped("ALTER TABLE others . victims ADD COLUMN x INT", "public")
  -> accepted (should throw)
```

Every schema-scoped change-set statement can target/create objects in a **foreign
namespace** simply by spelling `schema . object` with spaces, defeating the
"change-set SQL is bound to the configured namespace" guarantee. (The
session-namespace guard is not affected — its `set_config\s*\(` alternative still
matches.)

**Fix:** change the pattern to `IDENT + "\\\s*\.\\\s*" + IDENT` and add a bypass
regression test.

## P1 findings

### P1-1. No online index strategy — sync can block writes on large tables

`IndexDefinition.parse()` structurally rejects `CREATE INDEX CONCURRENTLY`, and index
creation runs inside the synchronization transaction on PostgreSQL/SQL Server. On a
large table an auto-created index holds a write-blocking lock for the whole build.
Auto-applied type widenings (`INTEGER -> BIGINT`, `VARCHAR -> TEXT`) similarly rewrite
large tables at startup. Enterprises need at minimum: (a) documented sizing guidance,
(b) an opt-out converting index creation to `pendingSql`, ideally (c) a PostgreSQL
`CONCURRENTLY` path executed outside the transaction.

### P1-2. MySQL/MariaDB history ledger `applied_at TIMESTAMP` is 32-bit (Y2038)

`DialectSupport.createHistoryDdl` uses `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`
for the MySQL family. MySQL/MariaDB `TIMESTAMP` ends 2038-01-19; a change-audit ledger
is exactly the artifact enterprises keep for decades. Use `DATETIME(3)`, and provide
the same migration hook already used for `applied_by` on already-deployed history tables.

### P1-3. Dry-run coupling on the implicit-DDL path is fragile

Declarative execution is dry-run-safe only because the guard lives in the private
`SchemaSynchronizer.execute()`. But `ChangeSetExecutor` has its own unguarded
`execute()` (ChangeSetExecutor.java:267) whose only dry-run protection is caller
branching, and `validateHistory()` still executes `verificationSql` during dry-run for
`ddlMayCommitImplicitly()` dialects (contradicting the comment at
ChangeSetExecutor.java:55). `executeControl()` also runs `SET search_path` /
`sp_getapplock` for real during dry-run. No mutation results today, but this is one
refactor away from a dry run that commits DDL on MySQL/Oracle. Centralize the dry-run
gate in a single guarded executor.

### P1-4. Ledger requires eternal change-set retention; no baselining

`ChangeSetExecutor.validateHistory()` throws when any *applied* change id is missing
from the current definition. Once a project accumulates change sets they can never be
pruned, merged, or baselined (no Flyway-`baseline` equivalent). For long-lived
enterprise databases this makes the definition file grow monotonically and blocks
adoption against databases that already match the schema. Provide a baseline/adopt mode.

### P1-5. Oracle runtime depends on a `DBMS_LOCK` grant

`DialectSupport.requestOracleLock` calls `DBMS_LOCK.REQUEST`; the publish pipeline even
runs `GRANT EXECUTE ON DBMS_LOCK` for its test user. Many enterprise DBA policies
revoke `DBMS_LOCK` from application schemas, and failure surfaces as an opaque
`IllegalStateException`. Document the prerequisite and improve the error message.

### P1-6. No dependency-vulnerability / supply-chain automation

No Dependabot/renovate config, no OWASP dependency-check or Snyk step, no CodeQL, and
no SBOM (CycloneDX) attached to releases. Current pins are fine (jackson-databind
2.18.3, postgresql 42.7.5 — both past known CVEs), but enterprise procurement
increasingly requires automated scanning attestations. The workflows already pin
GitHub actions by SHA — extend that rigor to dependencies.

### P1-7. CLI hides root causes

`SchemaSynchronizerCli.run()` prints only `exception.getMessage()`; any NPE, driver
issue, or `SQLException` chain (including the `nextException` chains the library
carefully builds) is invisible in ops logs. Print the stack trace (or full cause chain)
to stderr.

## P2 findings

1. **`ThreadLocal<List<String>> plannedSql` in `SchemaSynchronizer`** — thread-confined
   mutable state in a public class is a maintenance hazard; an explicit parameter is
   safer. The `remove()` in `finally` is correct today, but any new early-return adds
   a leak path.
2. **Library/CLI conflation** — `main`/`dryRunMain`/`validateMain` live inside
   `SchemaSynchronizer`, and its constructor accepts a `null DataSource` (the CLI passes
   `null`). Calling `synchronizeFromClasspath()` on such an instance NPEs. Move CLI
   entry points to the CLI module and validate constructor arguments.
3. **`SchemaSynchronizerInitializer` discards the result** — `afterPropertiesSet()`
   ignores `SchemaSynchronizationResult`; nothing is logged at the Spring level about
   what changed, and there are no Micrometer hooks. Emit a summary log and metrics.
4. **`NonDestructiveAlterPlanner.formatType`** silently widens beyond the request:
   `VARCHAR(20000)` becomes unbounded `VARCHAR`; preserve the declared length or reject
   lengths ≥ 10,000.
5. **`SchemaSynchronizerProperties` lacks validation** (no JSR-303/`@Validated`), and
   `advisoryLockId` cannot be overridden on the CLI path (hard-coded default).
6. **Repo hygiene** — `.kilo/worktrees/sour-knuckle` (stale AI worktree with outdated
   source copies), untracked `.agents/` and `skills-lock.json`, and personal career
   docs (`docs/RESUME_DESCRIPTION.md`, `docs/LINKEDIN_ARTICLE_READY_TO_PASTE.txt`)
   should be removed/ignored before enterprise consumption.
7. **Sensitive data in logs** — planned/pending SQL and change-set statements are logged
   verbatim at INFO; backfill `UPDATE`s can contain PII. Document a redaction approach
   in OPERATIONS.md.
8. **Unrestricted `GRANT` in allowed statements** (including MySQL `*.*` grants) and
   arbitrary `SELECT ... fn()` in change sets. Consistent with the "trusted artifact"
   scope in SECURITY.md, but least-privilege reviews will ask for a static warning when
   `GRANT` targets global objects.

## Dedicated Oracle & SQL Server pass (second review)

A focused second pass on the Oracle and SQL Server code paths (column plans, type
serialization, schema binding, locking, history DDL) with empirical verification of the
parser against the exact `TYPE_NAME` strings the JDBC drivers report.

### ORA-1 (P0). Oracle `TIMESTAMP … WITH TIME ZONE` columns break the whole sync (verified)

ojdbc reports `TIMESTAMP(6) WITH TIME ZONE` / `TIMESTAMP(6) WITH LOCAL TIME ZONE` as the
column `TYPE_NAME`. `ColumnDefinitionParser` cannot parse those forms:

```
ColumnDefinitionParser.parse("TIMESTAMP(6) WITH TIME ZONE NOT NULL")
  -> "unparseable column type"  (throws)
```

`SchemaSnapshotWriter.buildDefinition` happily *writes* that exact string into the
definition (default branch: `typeName + nullable`), so the serialize → sync loop is
self-breaking: any Oracle table containing a TSTZ column (the type Oracle tools use for
`SYSTIMESTAMP`-style columns) produces a `schema-definition.json` that fails
`validateDeclarative` and aborts the entire startup sync. The Oracle integration test
only uses `NUMBER` / `VARCHAR2`, so CI/publish never sees it.

**Fix:** teach `ColumnDefinitionParser.TYPE_LEN` / `normalizeType` the
`TIMESTAMP(<p>) WITH [LOCAL] TIME ZONE` forms (map to `TIMESTAMPTZ`), and add unit
tests using the ojdbc `TYPE_NAME` strings.

### ORA-2 (P1). `GENERATED BY DEFAULT ON NULL AS IDENTITY` mis-parses (verified)

The 12c+ `ON NULL` identity variant (the default in APEX/ORDS schemas) is not matched
by the `IDENTITY` regex; only the trailing word `IDENTITY` is stripped and `DEFAULT`'s
greedy capture swallows the remainder:

```
parse("NUMBER NOT NULL GENERATED BY DEFAULT ON NULL AS IDENTITY")
  -> base=NUMERIC, defaultExpr="ON NULL AS"   (garbage)
```

Downstream `shouldSkipAlter` (contains `IDENTITY`) currently contains the damage during
reconcile, but the `ColumnSpec` is wrong and any future code path trusting
`defaultExpr` mis-fires. Parse or reject the `ON NULL` form explicitly.

### ORA-3 (unverified — needs a live container). Oracle identity round-trip depends on ojdbc `IS_AUTOINCREMENT`

`SchemaSnapshotWriter.buildDefinition` appends ` GENERATED BY DEFAULT AS IDENTITY` only
when the driver reports `IS_AUTOINCREMENT=YES`. Oracle JDBC's support for that optional
column is doubtful; if it reports `NO`, the serialized `createSql` silently drops the
identity clause, and bootstrapping a fresh table from that snapshot creates a plain
`NUMBER` column whose `INSERT`s leave `id` NULL (the `PkIdentity` repair path is
PostgreSQL-only). The Oracle integration test never round-trips the *serialized*
definition, so this is untested. Add an assertion that the serialized definition of an
identity column still contains the identity clause, run against the
`gvenzl/oracle-xe` container.

### ORA-4 (architecture). Implicit-commit recovery is well designed but recovery is manual

Oracle DDL commits mid-transaction, so `validateHistory()` correctly refuses unapplied
changes lacking `verificationSql` (and multi-statement changes that are not yet
verified). The consequence for operators: partial declarative DDL executed before a
later failure **cannot be rolled back** — the sync leaves a half-converged schema and
recovery is manual. This is inherent to Oracle, but should be stated explicitly in
`docs/OPERATIONS.md` for Oracle/MySQL (the implicit-DDL preflight reduces but does not
eliminate the window).

### MSSQL-1 (P0). `VARCHAR(MAX)` / `NVARCHAR(MAX)` are unparseable — and the serializer emits exactly that (verified)

`portableVarchar` emits `VARCHAR(MAX)` for SQL Server `size >= 10_000` columns, but the
parser's `TYPE_LEN` regex only accepts digits inside the parens:

```
ColumnDefinitionParser.parse("VARCHAR(MAX) NOT NULL") -> throws "unparseable column type"
```

`MAX` columns are ubiquitous in SQL Server schemas, so serialize → sync is broken for
most real databases. **Fix:** accept `VARCHAR(MAX)` / `NVARCHAR(MAX)` in `TYPE_LEN`, map
to an explicit `MAX` length in `ColumnSpec`, and handle it in
`NonDestructiveAlterPlanner.classifyTypeChange`/`formatType` (MAX never auto-narrows).

### MSSQL-2 (P0). `VARBINARY(MAX)` silently becomes `VARBINARY(1)` (verified)

`buildDefinition`'s default branch (`typeName + nullable`) drops the length entirely for
`VARBINARY`, and `addColumnSql` emits:

```
ALTER TABLE docs ADD blob VARBINARY   -> SQL Server creates VARBINARY(1) — one byte
```

A drift or bootstrap that adds a binary column creates a **one-byte** binary column:
every value truncates to 1 byte at insert time. Silent wrongness, no error. Also
`VARBINARY(MAX)`-sized columns compare as `SAME` in drift detection (length is dropped
on both sides). Same class of issue: `DATETIME2(7)`/`DATETIMEOFFSET(7)` scale silently
dropped (P2 precision drift undetected). **Fix:** emit `VARBINARY(MAX)` when
`COLUMN_SIZE` is 2^31-1 (mirroring `portableVarchar`) and make the parser/planner
`MAX`-aware.

### MSSQL-3 (P1, high confidence — verify live). `sqlServerColumnPlan` ignores DEFAULT constraints

SQL Server refuses `ALTER COLUMN` on a column that has a default constraint
(Msg 5074: dependent object `DF__…`). The planner emits a bare
`ALTER TABLE t ALTER COLUMN c <definition>` for auto-safe widenings and never drops or
recreates the default constraint, so widening *any column that carries a default*
fails the sync. The integration test widens `label VARCHAR(40) → VARCHAR(100)` with no
default, so CI does not cover it. Fix: plan `DROP CONSTRAINT <name>` / re-`ADD` around
the `ALTER COLUMN`, or route defaulted-column widenings to `pendingSql`.

### MSSQL-4 (verified, limitation). Schema binding works only because the driver exposes the truth

`bindSqlServerSchema` calls `conn.setSchema(...)`, but mssql-jdbc's `setSchema()` is a
client-side no-op — SQL Server has no session-level current-schema concept (confirmed by
the mssql-jdbc maintainers, PR #890). The binding check still fails closed because
`getSchema()` runs `SELECT SCHEMA_NAME()` (the login's real default schema) and the code
asserts it equals the configured schema. Consequences:

- Supported topology is strictly **configured schema == login default schema**
  (e.g. `schema-synchronizer.schema=dbo`). Managing a *non-default* schema is
  impossible on SQL Server (unlike PostgreSQL, where `SET LOCAL search_path` handles it).
- Unqualified declarative DDL (`ALTER TABLE t ADD …`, `CREATE INDEX … ON t`) resolves
  to the default schema, which the assertion guarantees equals the configured schema —
  so name resolution is safe, but document the constraint; enterprises commonly
  provision logins whose default schema differs from the managed schema.

### Positive verification (Oracle / SQL Server)

- `oracleColumnPlan` emits valid Oracle `ALTER TABLE t MODIFY (col …)` syntax with
  correct `NULL`/`DEFAULT` clause reconstruction; the pending branch is sound.
- `sp_getapplock`/`sp_releaseapplock` usage is correct (`@LockOwner='Session'` survives
  the sync's commit/rollback; result codes `< 0` treated as failure; 30s timeout
  matches the other dialects).
- Oracle history DDL correctly swallows ORA-00955 in the `EXECUTE IMMEDIATE` exception
  handler; `DBMS_LOCK.REQUEST/RELEASE` statuses are handled with legacy dual-key
  acquisition for rolling upgrades; duplicate-object codes (955/1430/957/2260/2261)
  are correctly classified.
- `requireOracleSchema` (connected user must equal configured schema) and the metadata
  uppercase-folding for Oracle lookups are both correct.
- SQL Server history DDL (`OBJECT_ID` guard, `COL_LENGTH` guard for `applied_by`) is
  idempotent and correct; `sqlServerColumnPlan` correctly routes default changes to
  `pendingSql` (constraint-based defaults).
- `DATETIME2`/`DATETIMEOFFSET`/`UNIQUEIDENTIFIER`/`BIGINT … IDENTITY(1,1)` definition
  forms all parse correctly (verified).

## What is done well (verified in code)

- **Fail-closed verification queries**: exactly one non-null boolean row required
  (`ChangeSetExecutor.isVerified`), and duplicate-object adoption demands
  `verificationSql` so partial applies cannot be ledgered.
- **SQL safety engineering**: identifier allowlisting (`[a-zA-Z_][a-zA-Z0-9_]*`) on
  every interpolated name; comment/string/dollar-quote-aware masking before token
  checks; duplicate-object classification by SQLState/vendor code only (no
  message-substring fail-open); data-uniqueness violations never treated as
  "already exists".
- **Concurrency**: dual-key advisory locks with legacy-compat acquisition for rolling
  upgrades on all five dialects; savepoint-per-statement adoption; lock release in
  `finally` with suppressed-exception hygiene; savepoint-aware `SET LOCAL search_path`
  save/restore on the embedded-transaction path.
- **Change ledger**: SHA-256 checksums over id+statements+verification+phase, immutable
  applied entries, duplicate-row detection, `applied_by` audit column.
- **Spring integration**: opt-in (`enabled` default off), backs off on multiple
  DataSources, correct initializer-detector registration, ordered before Hibernate.
- **Release engineering**: GPG-signed, tag↔version check, Oracle gate before publish,
  SHA-pinned actions, atomic snapshot file writes, Percona/TiDB certification script.
