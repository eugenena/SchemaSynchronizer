# Design: desired-state schema evolution

SchemaSynchronizer keeps relational databases aligned with a version-controlled
desired-state definition. Deployments can apply routine additive changes
automatically, while destructive or ambiguous changes stay under operator control.

A migration history answers: **How did we get here?**

A desired-state definition answers: **What must the database look like now?**

SchemaSynchronizer is built around the second question.

## Safety boundary

The library reads a JSON definition, inspects the live database through JDBC,
computes the difference, and converges toward the declared state.

It divides schema evolution into three categories:

1. **Safe additive changes are automatic.** Creating a missing table, adding a nullable
   column, creating an index, widening a compatible type, or relaxing nullability can
   be applied directly.
2. **Destructive or ambiguous changes are reported, not executed.** Dropping a table or
   column, narrowing a type, replacing a primary key, or rebuilding a drifted index is
   returned as explicit, reviewable SQL in `pendingSql`.
3. **Operations that carry business meaning are intentional change sets.** Foreign
   keys, check constraints, data backfills, functions, triggers, and similar operations
   are expressed as ordered, checksummed changes with optional verification queries.

“Automatic” must never mean “unaccountable.”

## Why not execute every difference?

Two syntactically different database states are not always safely interchangeable.
Widening `VARCHAR(40)` to `VARCHAR(100)` is usually safe; narrowing may truncate data.
Adding a nullable column is straightforward; adding `NOT NULL` to a populated table may
require a default or backfill. Missing indexes can often be created automatically;
replacing an index can affect locking and availability.

When safety cannot be proven from metadata, SchemaSynchronizer produces the SQL an
operator would need and does not cross the approval boundary.

## Example definition

```json
{
  "tables": {
    "customers": {
      "createSql": "CREATE TABLE customers (id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, email VARCHAR(320) NOT NULL)",
      "columns": [
        { "name": "id", "definition": "BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL" },
        { "name": "email", "definition": "VARCHAR(320) NOT NULL" }
      ],
      "indexes": [
        "CREATE UNIQUE INDEX IF NOT EXISTS uq_customers_email ON customers (email)"
      ]
    }
  },
  "changes": []
}
```

## Operating models

- **Library API** for direct use from Java applications
- **Spring Boot** auto-configuration with explicit startup policies (boot sync is opt-in)
- **Standalone CLI** (`serialize` / `sync`) for deployment jobs that keep credentials out
  of process arguments (`SCHEMA_DB_PASSWORD` with `-`)

## Database support

Independently detected dialects:

- PostgreSQL
- MariaDB
- MySQL (compatibility targets include Percona Server and TiDB)
- SQL Server
- Oracle

Dialect support is explicit: products share SQL vocabulary but differ in metadata,
identifier limits, type rendering, DDL transaction semantics, and index syntax.
